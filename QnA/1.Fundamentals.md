## 1. FastAPI fundamentals

## FastAPI basics

### 1. What is FastAPI, and what problems does it solve?

- FastAPI is a modern, high-performance Python web framework used to build APIs.
- It is built on Starlette for web functionality and Pydantic for data validation.
- It supports asynchronous programming using `async` and `await`.
- It automatically generates interactive API documentation using Swagger UI and ReDoc.
- It provides automatic request validation, serialization, and type checking using Python type hints.
- It supports dependency injection, authentication, and security mechanisms.

Problems it solves:

- Simplifies REST API development in Python.
- Reduces boilerplate code through automatic validation and documentation.
- Improves performance for I/O-bound applications.
- Helps prevent invalid input through request validation.
- Makes API development easier to maintain and test.

Example:

```
from fastapi import FastAPIapp = FastAPI()@app.get("/")def home():    return {"message": "Hello, World!"}
```

- Run using: `uvicorn main:app --reload`
- Access Swagger documentation at: `/docs`

Interview one-liner: FastAPI is a modern Python framework for building fast, scalable, and type-safe APIs with automatic validation and interactive documentation.

---

### 2. How is FastAPI different from Flask and Django?

- FastAPI: Modern, high-performance framework designed primarily for API development.
- Flask: Lightweight micro-framework offering flexibility with minimal built-in features.
- Django: Full-stack framework providing built-in features such as ORM, authentication, admin panel, and templating.

Key Differences

| Feature           | FastAPI                  | Flask                                      | Django                                   |
| ----------------- | ------------------------ | ------------------------------------------ | ---------------------------------------- |
| Type              | API-focused framework    | Micro-framework                            | Full-stack framework                     |
| Performance       | High                     | Depends on deployment and workload         | Depends on deployment and workload       |
| Async support     | Built-in                 | Supported, with limitations                | Supported                                |
| Data validation   | Automatic using Pydantic | Usually requires extensions or manual code | Forms and serializers via tools like DRF |
| API documentation | Automatic                | Requires extensions                        | Requires additional tools                |
| ORM               | No built-in ORM          | No built-in ORM                            | Built-in ORM                             |
| Learning curve    | Moderate                 | Easy                                       | Moderate to steep                        |
| Best use case     | REST APIs, microservices | Small apps, lightweight APIs               | Full-featured web applications           |

When would you choose each?

- FastAPI: When building high-performance REST APIs, asynchronous services, or microservices.
- Flask: When building small applications or when you want maximum flexibility.
- Django: When building large web applications that need authentication, database management, and an admin panel.

Interview conclusion

- FastAPI provides automatic validation, type hints, and API documentation out of the box.
- Flask is simpler and more minimal.
- Django offers a comprehensive set of built-in web development features.
- My choice: I would choose FastAPI for an API-centric project requiring strong validation, asynchronous support, and high performance.

### 3. Why is FastAPI considered fast?

- Starlette: FastAPI uses Starlette for its web layer, which provides efficient request handling.
- ASGI support: It uses the Asynchronous Server Gateway Interface (ASGI), enabling efficient handling of concurrent requests.
- Async/await: Supports asynchronous programming for I/O-bound operations such as database queries and external API calls.
- Pydantic validation: Uses Pydantic for efficient data validation and serialization.
- Type hints: Python type hints help with validation, serialization, and developer productivity.
- Low overhead: FastAPI has relatively low framework overhead compared with many traditional web frameworks.
- High concurrency: It can handle many simultaneous I/O-bound requests without blocking a thread for each operation.

Example:

```
@app.get("/users")async def get_users():    users = await fetch_users_from_db()    return users
```

- Here, `await` allows the application to handle other work while waiting for the database operation to complete.
- Note: `async` improves concurrency for I/O-bound work; it does not automatically speed up CPU-intensive tasks.

Interview one-liner: FastAPI is considered fast because it uses Starlette, ASGI, and asynchronous programming to handle requests efficiently, while providing optimized validation and serialization.

### 4. What are ASGI and WSGI? Which one does FastAPI use?

- WSGI (Web Server Gateway Interface):
  - A standard interface between Python web applications and web servers.
  - Primarily designed for synchronous request handling.
  - Used by frameworks like Flask and traditional Django deployments.
- ASGI (Asynchronous Server Gateway Interface):
  - A modern interface supporting both asynchronous and synchronous request handling.
  - Supports HTTP, WebSockets, and long-lived connections.
  - Enables efficient concurrency for I/O-bound operations.

Key Differences

| Feature            | WSGI                           | ASGI                              |
| ------------------ | ------------------------------ | --------------------------------- |
| Processing model   | Primarily synchronous          | Sync and async                    |
| WebSockets         | Not natively supported         | Supported                         |
| Concurrency        | Typically thread/process-based | Supports asynchronous concurrency |
| Common servers     | Gunicorn, uWSGI                | Uvicorn, Hypercorn                |
| Framework examples | Flask                          | FastAPI                           |

Which one does FastAPI use?

- FastAPI uses ASGI.
- It commonly runs with Uvicorn, an ASGI server.
- ASGI allows FastAPI to handle asynchronous operations efficiently.

Example:

```
uvicorn main:app --reload
```

- `main`: Python file (`main.py`).
- `app`: FastAPI application instance.
- `--reload`: Automatically reloads the server during development.

Interview one-liner: WSGI is primarily designed for synchronous Python web applications, whereas ASGI supports asynchronous processing and WebSockets. FastAPI uses ASGI, commonly served by Uvicorn.

### 5. What are Starlette and Pydantic, and what role does each play?

- Starlette:
  - A lightweight ASGI framework that provides the web-handling foundation for FastAPI.
  - Handles routing, middleware, HTTP requests and responses, WebSockets, and background tasks.
  - Supports asynchronous request processing.
- Pydantic:
  - A Python library used for data validation and serialization.
  - Uses Python type hints to validate incoming request data.
  - Converts compatible input values into the required Python types and reports validation errors.
  - Helps define request and response schemas.

Key Differences

| Feature               | Starlette                             | Pydantic                     |
| --------------------- | ------------------------------------- | ---------------------------- |
| Primary role          | Web framework foundation              | Data validation              |
| Handles routing       | Yes                                   | No                           |
| Handles HTTP requests | Yes                                   | No                           |
| Validates data models | Not its primary role                  | Yes                          |
| Supports schemas      | Through web features and integrations | Yes                          |
| Used by FastAPI       | Web layer                             | Validation and serialization |

Example

```
from fastapi import FastAPIfrom pydantic import BaseModelapp = FastAPI()class User(BaseModel):    name: str    age: int@app.post("/users")async def create_user(user: User):    return user
```

- Starlette: Handles the HTTP request and routes it to the endpoint.
- Pydantic: Validates the request body against the `User` model.
- FastAPI: Integrates both and generates API documentation automatically.

Interview one-liner: Starlette handles the web layer, while Pydantic handles data validation and serialization. FastAPI combines both to simplify API development.

### 6. What happens when you start a FastAPI application?

- 1\. Application loading: Python loads the application module and creates the FastAPI instance.
- 2\. Server startup: Uvicorn starts as the ASGI server and loads the FastAPI application.
- 3\. Lifespan startup: Startup tasks run, such as initializing database connections, loading models, or creating shared resources.
- 4\. Route registration: FastAPI registers endpoints and their associated HTTP methods.
- 5\. Middleware setup: Configured middleware is applied to incoming requests and outgoing responses.
- 6\. Request listening: Uvicorn listens on the configured host and port for incoming requests.
- 7\. Request processing: When a request arrives, FastAPI matches the route, validates inputs, executes dependencies and the endpoint, and serializes the response.
- 8\. Response returned: The ASGI server sends the response back to the client.
- 9\. Shutdown: When the server stops, lifespan shutdown tasks run to release resources.

Example

```
from fastapi import FastAPIapp = FastAPI()@app.get("/")async def home():    return {"message": "Hello"}
```

Run the application:

```
uvicorn main:app --reload
```

- `main:app` identifies the application instance.
- `--reload` enables automatic reloading during development.

Request lifecycle ::

Client sends HTTP request

Uvicorn (ASGI server)

Middleware and routing

Validation and dependencies

Endpoint function executes

Response returned to client

Interview one-liner: When a FastAPI application starts, Uvicorn loads it as an ASGI application, runs lifespan startup tasks, and begins listening for requests. Each request passes through middleware, routing, validation, dependencies, and the endpoint before the response is returned.

| Validates request data      | Yes                   | No                   |

| Example                     | `app = FastAPI()`     | `uvicorn main:app`   |

Example

```

```

- `FastAPI()` creates the application.
- `uvicorn` runs the application as an ASGI server.
- `main` refers to `main.py`.
- `app` refers to the FastAPI instance.

Interview one-liner: FastAPI is the framework used to develop APIs, whereas Uvicorn is the ASGI server that runs the FastAPI application and handles network communication.

### 8. What is the difference between an API and a REST API?

- API (Application Programming Interface):
  - A general interface that allows two software applications to communicate.
  - Can follow different styles, such as REST, SOAP, GraphQL, or RPC.
  - Defines how applications request and exchange data.
- REST API (Representational State Transfer API):
  - A type of API that follows REST architectural principles.
  - Uses resources identified by URLs.
  - Commonly uses HTTP methods such as `GET`, `POST`, `PUT`, `PATCH`, and `DELETE`.
  - Typically exchanges data in JSON format.
  - Is generally stateless, meaning each request contains the information needed to process it.

Key Differences

| Feature      | API                             | REST API                        |
| ------------ | ------------------------------- | ------------------------------- |
| Meaning      | General communication interface | API following REST principles   |
| Architecture | Can follow different styles     | REST architectural style        |
| Protocol     | Can use different protocols     | Typically uses HTTP             |
| Data format  | JSON, XML, etc.                 | Commonly JSON                   |
| Rules        | Depends on API type             | Resource-oriented and stateless |

Example using FastAPI

```
from fastapi import FastAPIapp = FastAPI()@app.get("/users")def get_users():    return {"users": ["John", "Alice"]}@app.post("/users")def create_user():    return {"message": "User created"}
```

- `GET /users` retrieves users.
- `POST /users` creates a user.
- These endpoints demonstrate common REST-style API operations.

Interview one-liner

An API is a general mechanism for communication between software systems, whereas a REST API is an API that follows REST architectural principles, typically using HTTP methods and resource-based URLs.

## Routing and HTTP methods

## 1. What is a path operation in FastAPI?

- A path operation defines how an API responds to a specific URL path and HTTP method.
- It is created using decorators such as `@app.get()` and `@app.post()`.
- It connects an incoming request to a Python function called a path operation function.

Example:

```
@app.get("/users")
def get_users():
    return {"users": ["John", "Alice"]}
```

- `@app.get("/users")` defines the path operation.
- `/users` is the path.
- `get_users()` handles the request.
- The function's return value becomes the API response.

Interview one-liner: A path operation maps an HTTP method and URL path to a Python function that processes the request and returns a response.

---

## 2. Difference between `@app.get()`, `@app.post()`, `@app.put()`, `@app.patch()`, and `@app.delete()`

| Decorator       | Purpose                                   | Example              |
| --------------- | ----------------------------------------- | -------------------- |
| `@app.get()`    | Retrieve data                             | Get user details     |
| `@app.post()`   | Create a resource or trigger an operation | Create a user        |
| `@app.put()`    | Replace a resource                        | Replace user details |
| `@app.patch()`  | Partially update a resource               | Update user's email  |
| `@app.delete()` | Delete a resource                         | Delete a user        |

Example:

```
@app.get("/users/{user_id}")
def get_user(user_id: int):
    return {"user_id": user_id}

@app.post("/users")
def create_user():
    return {"message": "User created"}

@app.put("/users/{user_id}")
def replace_user(user_id: int):
    return {"message": "User replaced"}

@app.patch("/users/{user_id}")
def update_user(user_id: int):
    return {"message": "User partially updated"}

@app.delete("/users/{user_id}")
def delete_user(user_id: int):
    return {"message": "User deleted"}
```

Important interview points:

- `GET` is intended for retrieving data and should not modify server state.
- `POST` is commonly used to create resources.
- `PUT` generally replaces the complete resource representation.
- `PATCH` updates selected fields.
- `DELETE` removes a resource.
- `PUT` and `DELETE` are defined as idempotent HTTP methods; `POST` is generally not idempotent.

Interview one-liner: These decorators map HTTP methods to API operations: read, create, replace, partially update, and delete.

## 3. Difference between a path parameter and a query parameter

- Path parameter: Identifies a specific resource and is part of the URL path.
- Query parameter: Filters, sorts, searches, or paginates results and appears after `?` in the URL.

| Feature             | Path parameter               | Query parameter             |
| ------------------- | ---------------------------- | --------------------------- |
| URL example         | `/users/10`                  | `/users?age=25`             |
| Purpose             | Identify a resource          | Filter or customize results |
| Syntax              | `/users/{user_id}`           | `/users?age=25`             |
| Required by default | Yes, if declared in the path | Depends on its declaration  |

Example:

```
@app.get("/users/{user_id}")
def get_user(user_id: int):
    return {"user_id": user_id}

@app.get("/users")
def get_users(age: int):
    return {"age_filter": age}
```

- `/users/10` passes `10` as a path parameter.
- `/users?age=25` passes `25` as a query parameter.
- FastAPI validates the values against their declared types.

Interview one-liner: Path parameters identify which resource to access, while query parameters control how the requested data is filtered or retrieved.

## 4. How do you make a query parameter optional?

- Give the parameter a default value of `None`.
- FastAPI treats the parameter as optional because it no longer has to be supplied.
- Use `str | None` in modern Python to indicate that the value can be a string or `None`.

Example:

```
@app.get("/users")
def get_users(city: str | None = None):
    if city:
        return {"city": city}

    return {"message": "Returning all users"}
```

Usage:

- `/users` — works without a city.
- `/users?city=Pune` — filters by Pune.

For an optional parameter with a default value:

```
@app.get("/products")
def get_products(limit: int = 10):
    return {"limit": limit}
```

- If `limit` is omitted, it defaults to `10`.
- If supplied, FastAPI validates that it is an integer.

Interview one-liner: I make a query parameter optional by providing a default value, commonly `None`, in the function signature.

---

## 5. How do you set default values and validate query parameters?

- Use Python type hints to define the expected data type.
- Assign default values to make parameters optional.
- Use `Query()` from FastAPI to enforce constraints such as minimum values, maximum values, string length, and regular expressions.

Example:

```
from fastapi import FastAPI, Query

app = FastAPI()

@app.get("/products")
def get_products(
    limit: int = Query(default=10, ge=1, le=100),
    search: str | None = Query(
        default=None,
        min_length=2,
        max_length=50
    )
):
    return {
        "limit": limit,
        "search": search
    }
```

Explanation:

- `default=10` — uses 10 when `limit` is omitted.
- `ge=1` — requires `limit` to be greater than or equal to 1.
- `le=100` — limits `limit` to 100.
- `min_length=2` — requires at least two characters in `search`.
- `max_length=50` — allows at most 50 characters.
- Invalid inputs automatically produce a validation error response, typically HTTP `422`.

Example requests:

| Request               | Result                      |
| --------------------- | --------------------------- |
| `/products`           | Valid; limit defaults to 10 |
| `/products?limit=20`  | Valid                       |
| `/products?limit=200` | Validation error            |
| `/products?search=a`  | Validation error            |

Interview one-liner: I use type hints and default values for basic validation, and FastAPI's `Query()` for additional constraints. FastAPI validates incoming values automatically and returns errors for invalid inputs.

## 6. What is `APIRouter`, and why should you use it?

- `APIRouter` is used to organize API endpoints into separate, reusable modules.
- It helps structure large FastAPI applications by feature, such as users, products, and orders.
- It supports prefixes, tags, dependencies, and route-level configurations.
- Routers are registered with the main application using `app.include_router()`.

Example:

```
# users.py
from fastapi import APIRouter

router = APIRouter()

@router.get("/")
def get_users():
    return {"users": ["John", "Alice"]}
```

```
# main.py
from fastapi import FastAPI
from users import router

app = FastAPI()
app.include_router(router, prefix="/users")
```

- Endpoint: `GET /users/`
- Benefit: Improves modularity, maintainability, and code reusability.

Interview one-liner: `APIRouter` helps organize related endpoints into separate modules, making large FastAPI applications easier to maintain.

---

## 7. How do you add a prefix and tags to a router?

- Prefix: Adds a common path to every endpoint in the router.
- Tags: Groups endpoints in Swagger UI documentation.

Example:

```
from fastapi import FastAPI, APIRouter

app = FastAPI()

router = APIRouter(
    prefix="/users",
    tags=["Users"]
)

@router.get("/")
def get_users():
    return {"users": []}

@router.get("/{user_id}")
def get_user(user_id: int):
    return {"user_id": user_id}

app.include_router(router)

```

- `prefix="/users"` — both endpoints start with `/users`.
- `tags=["Users"]` — groups both endpoints under Users in `/docs`.
- Resulting endpoints:
  - `GET /users/`
  - `GET /users/{user_id}`

Interview one-liner: A router prefix avoids repeating common URL paths, while tags organize related endpoints in the API documentation.

## 8. What is the difference between returning a dictionary and returning a `Response` object?

- Returning a dictionary:
  - FastAPI automatically converts it to JSON.
  - Uses the default JSON response behavior.
  - Works with response-model validation and serialization when configured.
- Returning a `Response` object:
  - Gives direct control over the response body, status code, headers, and media type.
  - Can return JSON, plain text, HTML, or other content.
  - A directly returned response bypasses FastAPI's automatic response-model conversion and validation.

Example:

```
from fastapi import FastAPI
from fastapi.responses import JSONResponse

app = FastAPI()

@app.get("/users")
def get_users():
    return {"name": "John"}

@app.get("/custom")
def custom_response():
    return JSONResponse(
        content={"message": "Created"},
        status_code=201,
        headers={"X-App": "Demo"}
    )
```

| Feature            | Dictionary                  | `Response` object         |
| ------------------ | --------------------------- | ------------------------- |
| JSON conversion    | Automatic                   | Depends on response class |
| Custom headers     | Not directly                | Yes                       |
| Custom status code | Use decorator configuration | Yes                       |
| Response control   | Framework-managed           | More direct control       |

Interview one-liner: Returning a dictionary lets FastAPI serialize the data automatically, whereas returning a `Response` object gives explicit control over the HTTP response.

## 9. What is a `response_model`, and why is it useful?

- `response_model` defines the expected structure of an API response using a Pydantic model.
- FastAPI validates and serializes the returned data against the model.
- It helps filter out fields that should not be exposed to clients.
- It generates accurate response schemas in OpenAPI documentation.
- It improves consistency and type safety.

Example:

```
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class UserResponse(BaseModel):
    id: int
    name: str

@app.get("/users/{user_id}", response_model=UserResponse)
def get_user(user_id: int):
    return {
        "id": user_id,
        "name": "John",
        "password": "secret"
    }
```

Expected response:

```
{
  "id": 1,
  "name": "John"
}
```

- The `password` field is excluded because it is not part of `UserResponse`.
- Invalid response data generally causes a server-side response validation error.
- This is useful for preventing accidental exposure of sensitive fields.

Interview one-liner: `response_model` defines, validates, and serializes the API response structure, improves documentation, and helps prevent unintended data exposure.

## 10. How do you set a custom HTTP status code for an endpoint?

- Use the `status_code` parameter in the route decorator.
- You can use standard HTTP status codes such as `200`, `201`, `204`, and `404`.
- Use `HTTPException` when you need to return an HTTP error from inside the endpoint.

Example 1: Set a status code in the decorator

```
from fastapi import FastAPI, status

app = FastAPI()

@app.post("/users", status_code=status.HTTP_201_CREATED)
def create_user():
    return {"message": "User created"}
```

- Returns HTTP `201 Created` when the endpoint succeeds.
- `status.HTTP_201_CREATED` is a readable constant for status code `201`.

Example 2: Raise an HTTP error

```
from fastapi import HTTPException

@app.get("/users/{user_id}")
def get_user(user_id: int):
    if user_id <= 0:
        raise HTTPException(
            status_code=400,
            detail="Invalid user ID"
        )

    return {"user_id": user_id}
```

- Invalid IDs return HTTP `400 Bad Request`.
- Valid IDs return the normal successful response.

Interview one-liner: I set a default endpoint status using `status_code` in the route decorator and use `HTTPException` to return appropriate HTTP errors dynamically.

## Request data and Pydantic

## 1. What is a Pydantic model?

- A Pydantic model is a Python class used to define and validate the structure of data.
- It inherits from `BaseModel`.
- It uses Python type hints to validate and parse incoming data.
- It supports nested models, default values, constraints, and serialization.
- FastAPI uses Pydantic models to validate request bodies and structure responses.

Example:

```
from pydantic import BaseModel

class User(BaseModel):
    name: str
    age: int

user = User(name="John", age=25)
```

- `name` must be a string.
- `age` must be an integer or a value Pydantic can validly convert to an integer.

Interview one-liner: A Pydantic model defines a data schema and automatically validates and serializes data based on Python type annotations.

---

## 2. How does FastAPI validate a JSON request body?

- Define a Pydantic model representing the expected JSON structure.
- Declare that model as a parameter in the endpoint function.
- FastAPI reads the request body and validates it using Pydantic.
- Valid data is passed to the function as a model instance.
- Invalid data results in a validation error, typically HTTP `422`.

Example:

```
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class User(BaseModel):
    name: str
    age: int

@app.post("/users")
def create_user(user: User):
    return user
```

Request body:

```
{
  "name": "John",
  "age": 25
}
```

- FastAPI validates the fields and passes the validated `User` object to `create_user()`.
- You can access the values using `user.name` and `user.age`.

Interview one-liner: FastAPI uses Pydantic models to parse and validate incoming JSON before executing the endpoint function.

---

## 3. What happens when a request contains invalid data?

- FastAPI detects validation errors before calling the endpoint function.
- It returns HTTP `422 Unprocessable Entity` by default.
- The response includes details such as the invalid field, error type, location, and message.
- The endpoint's business logic does not execute.
- Custom exception handlers can be used to customize the error response.

Example:

```
class User(BaseModel):
    name: str
    age: int

@app.post("/users")
def create_user(user: User):
    return {"name": user.name}
```

If the request contains:

```
{
  "name": "John",
  "age": "abc"
}
```

- Pydantic cannot convert `"abc"` to an integer.
- FastAPI returns HTTP `422`.
- The endpoint function is not executed.

Interview one-liner: Invalid request data triggers automatic validation errors, usually HTTP 422, before the endpoint's business logic runs.

## 4. What is the difference between a Pydantic model and a database model?

- Pydantic model: Defines data validation, serialization, and API request or response schemas.
- Database model: Defines how data is stored and mapped to database tables or documents.
- Pydantic models are commonly used for API input and output.
- Database models are commonly defined using an ORM such as SQLAlchemy.
- A single application can use both models for the same entity.

Example:

```
from pydantic import BaseModel
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column
from sqlalchemy import String

class UserCreate(BaseModel):
    name: str
    email: str

class Base(DeclarativeBase):
    pass

class UserDB(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(100))
    email: Mapped[str] = mapped_column(String(255))
```

| Feature      | Pydantic model    | Database model                 |
| ------------ | ----------------- | ------------------------------ |
| Main purpose | Validate API data | Store and retrieve data        |
| Defines      | Data schemas      | Tables, columns, relationships |
| Used by      | FastAPI           | Database ORM                   |
| Example      | `UserCreate`      | `UserDB`                       |

Interview one-liner: Pydantic models validate and serialize application data, whereas database models represent persistent data and its database structure.

## 5. What is the difference between required, optional, and nullable fields?

- Required: The field must be provided.
- Optional: The field does not have to be provided.
- Nullable: The field is allowed to contain `None` or JSON `null`.
- Optional and nullable are not the same.

Example using Pydantic v2:

```
from pydantic import BaseModel

class User(BaseModel):
    name: str
    nickname: str | None
    age: int = 18
    email: str | None = None
```

| Field             | Required?    | Allows `None`? |
| ----------------- | ------------ | -------------- | --- |
| `name: str`       | Yes          | No             |
| `nickname: str \\ | None`        | Yes            | Yes |
| `age: int = 18`   | No           | No             |
| `email: str \\    | None = None` | No             | Yes |

- `nickname` must be supplied, but its value can be `null`.
- `email` can be omitted or set to `null`.
- `age` defaults to `18` if omitted.

Interview one-liner: Required means the field must be present, optional means it can be omitted, and nullable means it can accept `None`. In Pydantic v2, `str | None` alone does not make a field optional.

## 6. What are `Field()`, `Query()`, `Path()`, and `Body()` used for?

- `Field()`
  - Defines constraints and metadata for Pydantic model fields.
  - Supports minimum values, maximum values, string lengths, and descriptions.
- `Query()`
  - Defines validation and metadata for query parameters.
- `Path()`
  - Defines validation and metadata for path parameters.
- `Body()`
  - Configures request body parameters, including embedding and metadata.

Example:

```
from fastapi import FastAPI, Query, Path, Body
from pydantic import BaseModel, Field

app = FastAPI()

class Product(BaseModel):
    name: str = Field(min_length=2, max_length=50)
    price: float = Field(gt=0)

@app.post("/products/{product_id}")
def create_product(
    product_id: int = Path(gt=0),
    search: str | None = Query(default=None, min_length=2),
    product: Product = Body()
):
    return {"product_id": product_id, "product": product}
```

Key constraints:

- `gt=0` — greater than zero.
- `ge=0` — greater than or equal to zero.
- `min_length=2` — minimum two characters.
- `max_length=50` — maximum 50 characters.

Interview one-liner: `Field()` validates Pydantic model fields, while `Query()`, `Path()`, and `Body()` configure and validate parameters from the URL query, URL path, and request body.

## 7. What is the difference between a list, a nested model, and a list of nested models?

- List: Contains multiple values of a specified type.
- Nested model: Uses one Pydantic model as a field inside another model.
- List of nested models: Contains multiple objects, each validated against another Pydantic model.

Example:

```
from pydantic import BaseModel

class Item(BaseModel):
    name: str
    price: float

class Order(BaseModel):
    tags: list[str]
    primary_item: Item
    items: list[Item]
```

Example JSON:

```
{
  "tags": ["electronics", "sale"],
  "primary_item": {
    "name": "Laptop",
    "price": 800
  },
  "items": [
    {"name": "Laptop", "price": 800},
    {"name": "Mouse", "price": 25}
  ]
}
```

- `tags` — list of strings.
- `primary_item` — one nested `Item` object.
- `items` — list of `Item` objects, each validated independently.

Interview one-liner: A list holds multiple values, a nested model represents an object inside another model, and a list of nested models represents multiple validated objects.

## 8. How do you validate that an amount is positive or that a string has a minimum length?

- Use Pydantic's `Field()` to define validation constraints.
- Use `gt=0` to require a positive amount.
- Use `min_length` to enforce a minimum string length.
- Invalid data triggers a validation error automatically.

Example:

```
from pydantic import BaseModel, Field

class Payment(BaseModel):
    amount: float = Field(gt=0)
    description: str = Field(min_length=3, max_length=100)
```

Validation rules:

- `amount=100` — valid.
- `amount=0` — invalid.
- `amount=-10` — invalid.
- `description="Pay"` — valid.
- `description="Hi"` — invalid.

Other useful constraints:

- `ge=0` — zero or positive.
- `le=100` — maximum numeric value of 100.
- `max_length=50` — maximum string length.
- `pattern=r"..."` — regular-expression validation.

Interview one-liner: I use Pydantic's `Field()` constraints, such as `gt=0` and `min_length=3`, to enforce business validation rules at the data-schema level.

## 9. What are model validators in Pydantic?

- Model validators are used to implement custom validation logic.
- They are useful when validation involves multiple fields or more complex business rules.
- Pydantic v2 provides `@model_validator` with `mode="before"`, `mode="after"`, and `mode="wrap"`.
- Field-specific validation can be implemented using `@field_validator`.

Example: Validate that the end date is after the start date

```
from datetime import date
from pydantic import BaseModel, model_validator

class Booking(BaseModel):
    start_date: date
    end_date: date

    @model_validator(mode="after")
    def validate_dates(self):
        if self.end_date <= self.start_date:
            raise ValueError("End date must be after start date")
        return self
```

How it works:

- `mode="before"` — validates or transforms raw input before normal model validation.
- `mode="after"` — validates the constructed model after field validation.
- `mode="wrap"` — wraps the standard validation process for custom control.
- Raising `ValueError` causes Pydantic to report a validation error.

Interview one-liner: Model validators implement custom validation rules, especially cross-field checks that cannot be handled by simple type hints or individual field constraints.

## 10. How do you prevent internal fields, such as password hashes, from appearing in API responses?

- Use a separate Pydantic response model containing only fields that clients are allowed to see.
- Set `response_model` on the endpoint.
- Avoid returning database objects or internal fields directly without a defined output schema.
- Use separate request and response models when their fields differ.

Example:

```
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class UserResponse(BaseModel):
    id: int
    username: str
    email: str

@app.get("/users/{user_id}", response_model=UserResponse)
def get_user(user_id: int):
    return {
        "id": user_id,
        "username": "john",
        "email": "john@example.com",
        "password_hash": "internal-secret"
    }
```

Response returned to the client:

```
{
  "id": 1,
  "username": "john",
  "email": "john@example.com"
}
```

- `password_hash` is excluded because it is not part of `UserResponse`.
- The response model provides a clear boundary between internal data and public API data.
- Directly returning a custom `Response` object can bypass automatic response-model filtering, so use it carefully.

Interview one-liner: I use dedicated Pydantic response models with FastAPI's `response_model` parameter to expose only approved fields and prevent sensitive internal data from leaking into API responses.

## 11. What are HTTP request and response headers?

- Request headers: Metadata sent by the client to the server.
- Response headers: Metadata sent by the server to the client.
- They provide information about content type, authentication, caching, and client preferences.

Examples:

- `Content-Type: application/json` — indicates the format of the request or response body.
- `Authorization: Bearer <token>` — sends authentication credentials.
- `Accept: application/json` — tells the server which response format the client prefers.
- `Cache-Control: no-cache` — controls caching behavior.

FastAPI example:

```
from fastapi import FastAPI, Header

app = FastAPI()

@app.get("/profile")
def get_profile(user_agent: str | None = Header(default=None)):
    return {"user_agent": user_agent}
```

- FastAPI's `Header()` extracts a request header.
- Response headers can be set using a `Response` object.

Interview one-liner: HTTP headers carry metadata about requests and responses, including authentication, content type, and caching information.

## 12. What are the common HTTP status codes?

| Status                      | Meaning                              | Typical use              |
| --------------------------- | ------------------------------------ | ------------------------ |
| `200 OK`                    | Request succeeded                    | Fetch user details       |
| `201 Created`               | Resource created                     | Create a user            |
| `204 No Content`            | Success with no response body        | Delete a resource        |
| `400 Bad Request`           | Invalid request                      | Malformed input          |
| `401 Unauthorized`          | Authentication is missing or invalid | Invalid access token     |
| `403 Forbidden`             | Access is not permitted              | Insufficient permissions |
| `404 Not Found`             | Resource not found                   | User ID doesn't exist    |
| `409 Conflict`              | Conflict with current resource state | Duplicate username       |
| `422 Unprocessable Content` | Request data failed validation       | Invalid Pydantic input   |

Important interview points:

- `401` relates to authentication; `403` relates to authorization.
- `201` is commonly used after successfully creating a resource.
- `204` means the response must not contain a message body.
- FastAPI typically returns `422` for request validation errors.

Interview one-liner: HTTP status codes communicate the result of a request, including success, client errors, authentication failures, and validation problems.

## 13. What is the difference between 401 Unauthorized and 403 Forbidden?

- 401 Unauthorized:
  - The client is not successfully authenticated.
  - Credentials may be missing, invalid, or expired.
  - The client may need to authenticate again.
- 403 Forbidden:
  - The server understands the request but refuses access.
  - The client may be authenticated but lack the required permission.
  - Re-authentication alone will not necessarily solve the problem.

Example:

```
from fastapi import FastAPI, HTTPException

app = FastAPI()

@app.get("/admin")
def admin():
    authenticated = True
    is_admin = False

    if not authenticated:
        raise HTTPException(401, "Authentication required")

    if not is_admin:
        raise HTTPException(403, "Admin access required")

    return {"message": "Welcome, admin"}
```

Interview one-liner: `401` means valid authentication has not been established, while `403` means the request is understood but access is denied.

## 14. What does idempotency mean? Which HTTP methods are typically idempotent?

- Idempotency means that repeating the same request has the same intended effect on the server as making it once.
- It is important for retries, network failures, and reliable API integrations.
- HTTP defines `GET`, `HEAD`, `OPTIONS`, `PUT`, and `DELETE` as idempotent methods.
- `POST` is generally not idempotent by default.
- `PATCH` may or may not be idempotent, depending on how the operation is designed.

Example:

- `PUT /users/10` with the same data repeatedly should leave the user in the same state.
- `DELETE /users/10` repeatedly should leave the user deleted, even if later responses differ.
- `POST /orders` repeated without duplicate protection might create multiple orders.

Interview one-liner: Idempotency means repeating a request has the same intended server-side effect as executing it once. It is particularly important when implementing safe retries.

## 15. What is the difference between PUT and PATCH?

- PUT:
  - Generally replaces the complete resource representation.
  - Is idempotent according to HTTP semantics.
  - Omitted fields may be reset or removed, depending on the API's replacement rules.
- PATCH:
  - Updates only the specified parts of a resource.
  - Can preserve fields that are not included in the request.
  - Idempotency depends on the particular patch operation.

Example:

Existing user:

```
{
  "name": "John",
  "email": "john@example.com",
  "age": 25
}
```

PUT request:

```
{
  "name": "John Smith",
  "email": "john.smith@example.com",
  "age": 26
}
```

PATCH request:

```
{
  "name": "John Smith"
}
```

- PUT supplies the full replacement representation.
- PATCH changes only the name, preserving the other fields if the API implements partial updates.

Interview one-liner: PUT generally replaces a resource, while PATCH modifies selected fields without requiring the complete resource representation.

## 16. What are request headers, cookies, and query parameters?

- Request headers: Carry metadata such as authentication tokens, content types, and client information.
- Cookies: Small pieces of data stored by the client and sent to the server according to cookie rules; often used for sessions and preferences.
- Query parameters: Values appended to a URL after `?`, commonly used for filtering, searching, sorting, and pagination.

Example URL:

```
GET /products?category=books&limit=10
```

- `category=books` and `limit=10` are query parameters.
- `Authorization: Bearer ...` is a request header.
- `session_id=abc123` might be sent in a `Cookie` header.

FastAPI example:

```
from fastapi import FastAPI, Header, Cookie

app = FastAPI()

@app.get("/info")
def get_info(
    user_agent: str | None = Header(default=None),
    session_id: str | None = Cookie(default=None),
    limit: int = 10
):
    return {
        "user_agent": user_agent,
        "session_id": session_id,
        "limit": limit
    }
```

Interview one-liner: Headers carry request metadata, cookies commonly maintain client session state, and query parameters customize the requested data.

## 17. What is JSON serialization?

- JSON serialization converts Python objects or data structures into JSON-compatible data for transmission.
- FastAPI uses its serialization mechanisms to convert returned data into an HTTP response.
- Pydantic models can be serialized into Python data using `model_dump()` and into JSON text using `model_dump_json()`.
- Deserialization is the reverse process: reading JSON and converting it into usable data structures.

Example:

```
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class User(BaseModel):
    name: str
    age: int

@app.get("/user")
def get_user():
    user = User(name="John", age=25)
    return user
```

Response:

```
{
  "name": "John",
  "age": 25
}
```

\- FastAPI serializes the returned Pydantic model into JSON for the client.

Interview one-liner: JSON serialization converts application data into JSON format so it can be transmitted over HTTP and understood by other systems.

## 18. What is pagination, and why is it important?

- Pagination divides a large dataset into smaller results returned across multiple requests.
- It reduces response size, memory usage, and unnecessary data transfer.
- It improves API responsiveness and client usability.
- Common approaches include offset-based, page-based, and cursor-based pagination.

FastAPI example:

```
from fastapi import FastAPI, Query

app = FastAPI()

@app.get("/products")
def get_products(
    skip: int = Query(default=0, ge=0),
    limit: int = Query(default=10, ge=1, le=100)
):
    products = ["Book", "Pen", "Laptop", "Phone"]
    return products[skip:skip + limit]
```

Example request:

```
GET /products?skip=0&limit=10
```

- `skip` specifies how many records to skip.
- `limit` specifies the maximum number of records to return.
- In a production API, pagination is normally applied in the database query rather than fetching the entire dataset first.

Interview one-liner: Pagination returns data in manageable chunks, improving performance and reducing bandwidth and resource consumption.

## 19. What is the difference between client-side and server-side validation?

- Client-side validation:
  - Runs in the frontend, such as a browser or mobile app.
  - Provides immediate feedback to users.
  - Improves user experience.
  - Can be bypassed and must not be trusted for security.
- Server-side validation:
  - Runs on the backend before business logic or data persistence.
  - Ensures incoming data follows the application's rules.
  - Protects against malformed or malicious requests.
  - Is essential even when client-side validation exists.

Example:

- Frontend checks whether an email field is empty.
- FastAPI validates the request using Pydantic.
- Backend business logic checks whether the email is already registered.

Interview one-liner: Client-side validation improves user experience, while server-side validation enforces trusted data rules and protects the application.

## 20. What makes an API RESTful?

- Resource-oriented URLs: Resources are identified using paths such as `/users/10`.
- Standard HTTP methods: Uses `GET`, `POST`, `PUT`, `PATCH`, and `DELETE` appropriately.
- Stateless communication: Each request contains the information needed to process it; the server does not rely on stored client session context for request interpretation.
- Uniform interface: Uses consistent resource representations and HTTP semantics.
- Client-server separation: Frontend and backend can evolve independently.
- Cacheability: Responses can indicate whether they are safe to cache.
- Layered architecture: Clients can interact through intermediaries such as gateways or proxies without needing to know the internal architecture.

Example:

| Method | Endpoint    | Operation               |
| ------ | ----------- | ----------------------- |
| GET    | `/users`    | List users              |
| GET    | `/users/10` | Retrieve a user         |
| POST   | `/users`    | Create a user           |
| PUT    | `/users/10` | Replace a user          |
| PATCH  | `/users/10` | Partially update a user |
| DELETE | `/users/10` | Delete a user           |

Interview one-liner: A RESTful API follows REST architectural constraints, including resource-based URLs, a uniform interface, stateless requests, and appropriate HTTP semantics.
